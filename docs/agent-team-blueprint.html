● BẢN THIẾT KẾ v3 — CHỜ DUYỆT

Agent Team & Control Tower

Bản thiết kế đầy đủ trước khi triển khai: 9 pipeline agents chạy flow 8 stage (có dev agents góc nhìn BE/FE riêng), 6 review agents độc lập theo vai trò, task board trong từng Unit với dependency — claim — approver, giao thức teammate để FE/BE làm rõ API contract trước khi code, vòng retro — lesson learned, governance DoR/DoD có version, và Control Tower theo dõi toàn bộ. Mọi quyết định và thay đổi của AI đều thành tài liệu truy vết được.

01 · Đội hình

Bốn nhóm, một nguyên tắc: AI thực thi — người quyết định

Đội hình chia bốn nhóm. Pipeline agents đẩy công việc qua 8 stage của AI-DLC. Review Board — các agent độc lập theo vai trò, không tham gia thực thi, chỉ review đúng đoạn thuộc chuyên môn và ra verdict. Learning — retro-keeper biến lesson learned thành nâng cấp skill cho agent. Hạ tầng quan sát ghi lại mọi trao đổi và hiển thị qua Control Tower.

02 · Workflow

Bản vẽ kết nối: ai làm gì, ai nói với ai, dừng ở đâu

Thứ tự bắt buộc trong một Bolt (stage 6)

DoR check (qa) → Domain Design → Logical Design → tech-lead + security review design → task board (bolt-coordinator) → contract freeze → be-dev ∥ fe-dev thực thi → BE/FE + security + qa review code & tests → Fix → Gate E (dev validate) → Acceptance

Tech Lead và Security chặn approach sai và lỗ hổng thiết kế trước khi code tồn tại — rẻ hơn nhiều so với review sau. Reviewer chỉ được gọi cho phần thuộc góc nhìn của mình; bolt thuần backend không gọi frontend-reviewer.

03 · Trong một Unit

Task board: dependency rõ, claim rõ, approver được assign sẵn

Khi một Unit đã rõ (qua Gate D), bolt-coordinator chia nó thành task board: mỗi task gắn góc nhìn (BE/FE), dependency, và approver được assign ngay từ đầu — không có task nào "xong" chỉ vì người làm nói xong. Luật cứng: task chỉ được claim khi mọi task nó phụ thuộc đã done và được approver có góc nhìn độc lập ký duyệt. Đoạn ráp nối nhạy cảm nhất — API giữa BE và FE — xử lý bằng contract handshake:

units/UOW-02/tasks.md                       # TASK BOARD — share cho mọi agent
## TSK-05 · Implement GET /onboarding/personal-info
perspective: BE
status: review                # todo · claimed · in-progress · blocked · review · done
claimed_by: be-dev            # claim ghi danh — một task một người nhận
approver: backend-reviewer    # assign sẵn từ lúc tạo board, không tự chọn
depends_on: TSK-03 (contract v2 frozen — đã được fe-dev đồng ý)
comms: MSG-0058 (fe-dev hỏi pagination) · MSG-0060 (chốt cursor-based)
notes: đổi offset → cursor sau trao đổi với fe-dev; contract v1→v2 (DEC-0024)
  • Tuần tự khi cần, song song khi được: dependency trên board là DAG — task độc lập chạy song song; task phụ thuộc bị khóa cứng tới khi upstream done + approver duyệt. Không có "làm trước rồi tính".
  • Claim minh bạch: agent claim task bằng cách ghi tên vào board (một dòng commit) — tower hiển thị ai đang giữ gì; task claimed quá lâu không tiến triển sẽ bị bolt-coordinator hỏi thăm qua MSG.
  • Mọi liên lạc dính vào task: field comms nối task với đúng các MSG đã trao đổi về nó — đọc một task là thấy lịch sử ai đã nói gì với ai, vì sao quyết như vậy.
04 · Giao tiếp & truy vết

Mọi trao đổi là file, mọi quyết định là DEC, mọi thay đổi có changelog

Agent không "nói chuyện miệng" — mọi giao tiếp đi qua message bus dạng file để truy vết được, hiển thị trên tower, và giữ qua nhiều phiên. Orchestrator route message và cập nhật status. Ba loại bản ghi tạo thành chuỗi truy vết đầy đủ:

context-memory/comms/MSG-0042.md          # ① TRAO ĐỔI
---
from: unit-planner
to: pm-po-reviewer
re: INT-001 / UOW-03
type: review-request        # review-request · finding · question · answer · clarification · handoff · note
status: answered            # open · answered · closed
---
Đề nghị review breakdown 5 Units cho INT-001. Risk chính: UOW-03
phụ thuộc data migration chưa rõ scope.
context-memory/reviews/RV-012.md          # ② REVIEW VERDICT
---
reviewer: tech-lead-reviewer
target: INT-001 / UOW-03 / design.md
verdict: request-changes    # approve · approve-with-notes · request-changes
checklist: review-approach v2, review-infra v1
---
[MUST] Sync call sang legacy API sẽ timeout với batch >500 records — chuyển qua queue.
[SHOULD] Thêm Redis chỉ để cache 1 endpoint — dùng in-memory trước, ghi vào tech-debt-register.
context-memory/decisions-log.md           # ③ QUYẾT ĐỊNH
## DEC-0018 · 2026-08-11 · Gate D · INT-001
- Quyết định: approve scope 5 Units, loại UOW-06 khỏi phase này
- Người quyết: HUMAN (anh/chị) · đề xuất bởi: unit-planner
- Căn cứ: RV-010 (pm-po approve-with-notes) · MSG-0042
- Ảnh hưởng: units/UOW-01..05 unlocked · changelog cập nhật
  • Chuỗi truy vết: mọi dòng code đều trace ngược được: code → design.md → UOW spec → DEC (gate approval) → RV (review) → MSG (trao đổi) → intent. Stage 8 verify chuỗi này đủ trước khi đóng intent.
  • No silent change: agent muốn đổi bất kỳ artifact nào đã qua duyệt (spec, design, DoD…) phải tạo DEC mới + một dòng changelog; nếu thay đổi ảnh hưởng scope thì gate tương ứng mở lại chờ anh/chị. Không có ngoại lệ.
  • Changelog hai cấp: mỗi intent có changelog.md riêng (những gì thay đổi trong intent đó), và changelog toàn cục ghi thay đổi về governance/skill (DoD đổi version, checklist được patch sau retro).
  • Escalation lên người: reviewer ra request-changes 2 lần cho cùng artifact → orchestrator dừng, đưa bất đồng vào Gate Queue chờ anh/chị quyết.
  • Ghi chú bắt buộc: mỗi agent kết thúc lượt làm việc phải ghi note tóm tắt việc đã làm + bàn giao gì — nguồn dữ liệu cho Agent Activity trên tower.
05 · Governance

DoR / DoD: định nghĩa thành văn, có version, có lịch sử

"Hoàn thành" và "sẵn sàng" không nằm trong đầu agent — chúng là hai tài liệu chuẩn trong context-memory/governance/, được mọi agent tham chiếu theo version, và chỉ được sửa qua DEC do anh/chị duyệt:

06 · Learning loop

Retro sau mỗi release: lesson learned trở thành skill mới của agent

Không có vòng này, agent lặp lại cùng một lỗi ở mọi intent. Sau mỗi Release (hoặc khi anh/chị gọi /retro), retro-keeper phân tích toàn bộ dấu vết của intent vừa xong — message nào lặp lại, review nào bị request-changes vì lý do gì, escalation nào phải lên người, gate nào bị reject — rồi chưng cất thành lesson và patch cụ thể vào checklist của agent liên quan:

context-memory/lessons-learned/LL-002.md
---

---
Lesson: các integration với legacy API đều có batch limit không tài liệu hóa.
Patch: thêm vào checklist review-approach: "hỏi batch limit / timeout của mọi
external call ngay ở bước Domain Design"; thêm DoD: "migration script phải có rollback test".
07 · Control Tower

Một màn hình trả lời: đang ở đâu, ai đang làm gì, cái gì chờ tôi

Bảy điểm dừng bắt buộc

Cộng thêm gate động: mọi escalation từ Review Board (2× request-changes), escalation teammate (logic sai từ đầu / tài liệu thiếu chạm scope), và mọi thay đổi artifact đã duyệt có ảnh hưởng scope đều thành điểm dừng chờ anh/chị. Tại mỗi gate A–D, ba-reviewer đính kèm decision brief (bối cảnh · phương án · trade-off · khuyến nghị) để anh/chị quyết nhanh, có căn cứ.

09 · Triển khai

Kế hoạch scaffold sau khi được duyệt

  1. .claude/agents/ — 17 agent definitions: 9 pipeline (có bolt-coordinator, be-dev, fe-dev) + 7 review board (có ba-reviewer) + retro-keeper, mỗi file ghi rõ vai trò, input/output, giao thức comms, luật claim và điều kiện gate.
  2. .claude/skills/ — commands điều khiển flow: /intent /discover /validate /units /bolt /tasks /accept /retro /status /tower + ~20 review checklists có version cho Review Board.
  3. context-memory/ — cấu trúc template: intents/, comms/, reviews/, lessons-learned/, governance/ (dor.md v1 + dod.md v1 để anh/chị duyệt nội dung ban đầu), decisions-log.md, changelog.md, risks.md, tech-debt-register.md.
  4. Control Tower generator — script đọc context-memory → render dashboard, publish lần đầu để anh/chị có URL cố định.
  5. CLAUDE.md — cập nhật để mọi phiên Claude Code sau đều hiểu đội hình, giao thức, luật gate và luật no-silent-change.
  6. Dry-run — chạy thử 1 intent mẫu (Foreign National Onboarding từ tài liệu AI-DLC) tới Gate D để anh/chị thấy flow, comms, DoR check và tower hoạt động thật.

Chờ anh/chị duyệt

Bản v3 bổ sung thêm: tầng thực thi trong Unit (bolt-coordinator + be-dev/fe-dev với góc nhìn riêng), task board có dependency — claim — approver assign sẵn, contract handshake FE↔BE trước khi code (trao đổi teammate có ghi lại, escalate khi logic sai từ đầu hoặc tài liệu thiếu), và ba-reviewer hỗ trợ anh/chị ra quyết định bằng decision brief tại gate A–D. Nếu đồng ý toàn bộ, trả lời "ổn" — tôi sẽ scaffold theo kế hoạch mục 09.

Muốn chỉnh phần nào (thêm/bớt reviewer, đổi vị trí gate, nội dung DoR/DoD ban đầu, thông tin tower hiển thị) — nói rõ, tôi cập nhật bản vẽ này trước rồi mới triển khai.
